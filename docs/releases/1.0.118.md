# 1.0.118 — retain command launch failures in worker context

Windows PowerShell now receives the original script directly as one `-Command`
argument. On the installed machine, the 1.0.117 base64 decode/execute wrapper
caused Defender to deny even `cmake --version; ninja --version` before launch.
The event identified that exact command line; plain source launched both tools
successfully with no security configuration change. Quoting, multiline source,
readable errors and native host exit semantics remain covered by regressions.

Command tools now return a structured `command_launch_failed` result when the
OS refuses to create the process. Previously, `PermissionError` and missing
executable errors escaped the tool and crashed the worker, discarding its
normal progress report and continuation. The result contains bounded, redacted
OS diagnostics, error numbers, shell/interpreter context and a null exit code;
there is no invented command output or successful execution.

The worker can investigate with authorized tools or report a concrete blocker.
There is no automatic retry, shell fallback or access-permission change.
Cancellation still propagates. Existing command denials and operator approvals
run before launch, and ordinary nonzero program exits retain their behavior.

Regression coverage includes all three launch paths, missing/denied/other OS
errors, redaction and bounded messages, a real failed OS launch followed by a
successful command, and a complete worker dialogue that retains the diagnostic
and subsequent command evidence without claiming completion. These controlled
results do not establish a live project-delivery gain. Other access denials
still require investigation of their actual OS diagnostic.
